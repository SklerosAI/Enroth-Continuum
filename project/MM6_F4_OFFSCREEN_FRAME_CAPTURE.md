# MM6 F4 offscreen first-map frame capture

Status: **monitored hidden OpenGL world and chest captures pass; normal new-game entry remains guarded** (2026-11-06). This is a test-only macOS diagnostic. It does not change MM7 startup or place a proprietary screenshot in Git.

## Capture contract

`GameTestOptions` accepts `--offscreen-gl` only for MM6 and only with `--gtest_also_run_disabled_tests --gtest_filter=MM6OffscreenFrame.DISABLED_FirstOutdoorCapture`. `GameStarter` uses the standard SDL platform and OpenGL renderer, installs `OffscreenCaptureGuard` before configuring the window, forces windowed mode and no mouse grab, and routes audio to the null driver. SDL creates its OpenGL window hidden. The guard refuses show/raise, cursor-visibility changes, mouse grabs/relative mode/warps and modal message boxes. The PNG destination must be a normalized absolute `.png` path under `/tmp` or `/private/tmp`.

The isolated test enters party creation from the menu, stages private game deltas and a deterministic MM6 chest owner in memory, then calls `GameUI_LoadPlayerPortraitsAndVoices` before scoped `DoPrepareWorld`, matching `Game::gameLoop`'s setup order. It draws the first outdoor world and HUD into the hidden OpenGL context, flushes the queued 2D vertices and text in the same order as `Engine::Draw`, then reads pixels before swap. It requires a 640×480 nonblank image with nonblack world and HUD regions plus chromatic pixels inside all four portrait faces, and writes the PNG only to the temporary path. Existing null-renderer tests retain their setup and platform; this process-global world test is disabled by default and must run alone.

A private macOS monitor sampled the process every 10 ms, comparing the frontmost application PID and counting its on-screen windows through `CGWindowListCopyWindowInfo`. The corrected arm64 run passed **1/1**, with **164 samples**, **zero on-screen windows** and **no focus change**. The first hidden-GL attempt also kept focus and windows unchanged but aborted while loading a directional actor sprite. The diagnostic PNG was inspected locally and remains ignored.

The same custom linked binary passed the MM7 `Inventory.Initialization` headless control **1/1** with no on-screen window or focus change (45 samples). A negative MM6 `--offscreen-gl` invocation with a different test filter was rejected before SDL startup. Parent integration should rerun the focused cases after cherry-picking; the standalone link reused the current green arm64 libraries and replaced only the changed objects.

## First render blocker and source-backed correction

The first world draw aborted at `SpriteFrameTable::InitializeSprite` when the MM6 `pfemsta` frame requested an unsuffixed sprite that the retained archive does not contain. The retained MM6 `dsft.bin` frame points to a seven-character directional texture prefix; the retained sprite archive contains its numbered octants. An aggregate check of all **981** eligible seven-character directional prefixes in that table found a numbered zero-octant entry for every prefix and no unsuffixed exact entry. The inherited `Sprites.cpp` path appended an octant only when the prefix length was **less than** seven. It now appends at seven for MM6 only; MM7 retains its original condition. A focused MM6 headless sprite test passed **1/1** with all eight octant pointers nonnull and no window/focus change. This correction is based on the retained original table/archive relationship; the accepted executable's sprite-loading branch was not independently reconstructed here.

## What the captured pixels show

The same isolated hidden test now accepts an optional second temporary PNG path for a first-open chest. It selects an untrapped item-bearing chest when available, opens it through the MM6 live owner transaction, renders the chest screen, checks that more than 10,000 pixels differ from the outdoor frame, and closes the GUI before engine teardown. The integrated hidden run passed **1/1** over 118 host samples with no visible window or focus change. The private capture was visually inspected: the chest panel and item icons occupy the expected area alongside the four-character HUD. The PNG remains local and untracked. This establishes only one rendered chest layout; trap, click pickup, persistence and campaign play remain guarded.

The earlier diagnostic had black party portrait ovals because the test read the framebuffer **before** `OpenGLRenderer::flushAndScale` submitted its queued portrait quads. The portrait-load call had already run. This was a capture-order error, not evidence of a missing MM6 portrait resource. The corrected image has four colored portraits and visible selected-character framing. The test checks chromatic pixels in each inner face region so this omission cannot silently recur.

The corrected capture has recognizable first-map sky, buildings, outdoor geometry, automap and HUD. The MM6 sprite-frame snapshot previously used MM7's 32-bit flags layout, reading the MM6 palette at the wrong offset. The [pinned MMExtension `SFTItem` schema](https://github.com/GrayFace/MMExtension/blob/a2ab9b12705de7576aecf8111168666d6398f830/Scripts/Structs/01%20common%20structs.lua#L2405-L2446) and retained `dsft.bin` agree: MM6 flags are 16-bit at offset 44, light radius at 46, palette at 48, frame time at 52 and total time at 54. MM7 keeps its 32-bit layout. The corrected hidden frame shows green `tree01` foliage and red `tree03` foliage; a private original-asset palette rendering confirms `tree03` is itself red. A focused headless tree-palette and portrait-cycle run passed **2/2** (78 monitor samples), and the final hidden frame passed **1/1** (73 samples); both had no on-screen window or focus change. The private image and asset extracts remain untracked.

The retained MM6 bitmap archive supplies `wtrtyl` and the original `wtrdr*` shore tiles, but not the MM7 `HDWTR` animation frames. MM6 tile-table reconstruction now keeps the original shore names, the MM6 shore masks make palette index zero transparent, and the seven renderer water layers read `wtrtyl`; the MM7 names and path remain unchanged. A synthetic title-isolation tile-table test passed **1/1**. A hidden run confirmed the CPU water bitmap and GPU layer-zero first pixel agree and the original shore images decode as expected. These corrections remove the missing inherited water-name lookups but do not establish correct terrain appearance.

The bright cyan ground with red rings in the earlier capture was the engine's `pending` placeholder image, not a color in the original water bitmap. The earlier diagnosis that the original map uses 209 tile-zero cells is superseded: its used terrain grid has no literal local tile ID zero. The inherited loader discarded four serialized MM6 tile selector bases and projected some types through a lossy MM7 tileset enum, producing 209 `pending` cells. The [selector packet](MM6_F4_OUTDOOR_TILE_SELECTORS.md) records the original-executable base-field trace and title-scoped correction. The next hidden capture exposed black ground because the renderer placed same-size MM6 water and land in water's GPU texture unit while its shader read land from unit one. An MM6-only allocator now places land in unit one. The integrated hidden recapture passed **1/1** over 130 samples with no window/focus change and shows land and road art; the measured black ground region has zero exact-black pixels. The old broad white foreground patch disappeared after the water-source correction; small pale upper-center pixels have an unproved billboard owner.

The earlier large cyan/red ground region has been removed. A monitored MM7 `Inventory.Initialization` control passed **1/1** (32 samples, no window or focus change) against the unchanged 60-byte MM7 frame layout. Complete visual correctness and normal gameplay remain unaccepted.

Next: verify MM6 seasonal and shoreline appearance against original behavior, then reassess the remaining small pale highlights. The six-frame selected-portrait animation, a foreground frame, actual party finalization and input acceptance remain separate gates.
