# MM6 chest map-load route — scoped integration seam

Status: **scoped opt-in source join, not a proved playable map load** (2026-11-06). The default MM6 path still reaches `generateChestItemsForTitle` and throws before inherited MM7 chest generation. MM7 still calls its inherited generator with no new preflight. No installed runtime, SaveLoad or GUI file was changed.

`Engine::_461103_load_level_sub()` runs after `loadAndPrepareBLV/ODM` has reconstructed `vChests` and saved the decoded MM6 active DLV/DDM in `pIndoor/pOutdoor->mm6DeltaBytes`. It now tries `mm6::tryActiveChestMapLoad` only for MM6. Without `ScopedChestMapLoadOptIn` on the loading thread, or if any validation fails, it calls the unchanged MM6 guard and stops. The scope is intended for headless integration acceptance; no production path constructs it yet.

The opt-in route requires an MM6 title, valid map ID/table treasure level, nonnull MM6 item table and party, and a ready title-local `ChestTitleState` seeded once at new game or restored from `.ec6` CHST. It scans the party's four inventories and held item for owned artifacts 400–429. The existing live adapter then checks exactly twenty chest records against the current runtime and decoded map sidecar, stages generation and projection for all twenty with copied LCG/artifact state, re-encodes the active sidecar, and publishes only after all checks pass. Missing seed/table/party/sidecar, malformed late record, or foreign title leaves chest, sidecar and title state unchanged. A failed opt-in attempt then reaches the old blocking guard.

The reusable `tryChestMapLoadBinding` uses the same scope, party scan and adapter against explicit test owners. A focused arm64 native link passed **3/3** synthetic outdoor tests: disabled scope leaves owners unchanged, seeded scope commits all twenty, foreign/missing/unready/malformed inputs roll back, and thirteen party-owned artifacts cap a direct reward. `Engine.cpp` passed focused C++ syntax, and C++ lint/diff whitespace passed. These tests do **not** execute `DoPrepareWorld`, first-map resource loading, `.ec6` autosave/restore, first-open UI or save–quit–load.

The separate `MM6ZChestHeadless.ScopedFirstOutdoorMapAndRollback` GameTest now passes **1/1** against the private MM6 archive under the null renderer. It populates the in-memory `pMapDeltas` from the archive's 67 default DLV/DDM entries, sets an explicit deterministic process CHST seed, invokes the real `OutdoorLocation::Load` for `oute3.odm`, then calls `tryActiveChestMapLoad` inside the scoped opt-in. It verifies all twenty runtime chest headers, 140 first-24-byte item projections and grids against the active decoded sidecar. A truncated active sidecar rejects a second transaction without changing `vChests`, LCG, generated flags or the malformed sidecar. The monitor reported **zero onscreen windows and no focus change**. No private asset bytes or names beyond the first-map identifier are tracked.

This proves the live chest owner join after actual first-map reconstruction, **not** the complete first-map transition. In the headless menu fixture, `DoPrepareWorld(false, 1)` stops before map loading at its one-window reset assertion. Calling `loadAndPrepareODM` after its actor-array setup reaches a separate `SpawnEncounter` abort because the MM6 monster-table lookup for a first-map encounter is unresolved. Calling `_461103_load_level_sub()` after direct `OutdoorLocation::Load` passes chest assertions but its inherited progress/GUI path requests absent `ib-autmask-a`; a forced fullscreen progress mode avoids that image request but leaves a synthetic event at GameTest teardown. The MM6 minimap-frame replacement is not yet validated, so none was guessed. These attempted runs used the null renderer and changed neither focus nor visible windows. The full outer transition and post-load UI remain closed gates; no normal MM6 path constructs the opt-in scope.

The first new-game autosave occurs before the `oute3.odm` transition and `Outdoor::Load`; the save workstream must stage a seeded CHST and default decoded `oute3.ddm` independently before map entry. The headless workstream owns the integrated first-map load and rollback test after that save stage lands. Only that integrated result can justify enabling the scoped route for normal MM6 play. The [live-owner adapter](MM6_F4_CHEST_LIVE_OWNER_ADAPTER.md), [first-open gate](MM6_F4_CHEST_INTERACTION_GATE.md) and [save checklist](../.llm-wiki/MM6-F4-Save-Transaction-Checklist.md) list further gameplay and persistence blockers.
