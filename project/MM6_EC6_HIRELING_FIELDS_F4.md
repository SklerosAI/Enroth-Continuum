# MM6 `.ec6` party hireling state — F4 offline progress

Status: **bounded `HIRE` v1 section and MM6-only capture/copy-staging; no live save/load** (2026-11-06).

`Party` has two `NPCData` hireling copies, two display-name strings and two `NPCSacrificeStatus` records. Hiring in the current source copies an NPC into one party slot and sets the corresponding display name; daily reset changes `hasUsedAbility` in those copies. Dark Sacrifice tracks `inProgress`, elapsed duration and end duration beside each copy, then removes the hireling when elapsed reaches end. The inherited MM7 snapshot overlays sacrifice state onto three NPC dialogue event fields. The new `.ec6` `HIRE` section keeps these as separate fields, preserving all six dialogue IDs rather than aliasing them with sacrifice timing. The private F3 logical manifest requires two paid follower slots but does not establish a native MM6 save wire layout; this is a new logical runtime snapshot.

`HIRE` stores exactly two full NPC records using the same bounded record codec as `RESC`: name, portrait, raw flags, fame/reputation, house, profession (including generic MM6 IDs), greeting/join, opaque `field_24`, six dialogue IDs, sex, ability-use value and news topic. It also stores each display-name copy and sacrifice flag/ticks. Names are at most 1,024 bytes without NUL; the payload is at most 4,276 bytes. Sacrifice ticks must be nonnegative and within the safe `Duration` conversion bound; an in-progress sacrifice needs a positive end duration. Decoding requires version one, exactly two slots, the required tag, valid record lengths and the outer `.ec6` checksum before assignment.

`captureHirelingFields` rejects non-MM6 titles and validates all fields. `stageHirelingParty` decodes first and applies the two hireling records, display names and sacrifice clocks to a party copy. It does not mutate global NPC tables or call hire/fire/sacrifice routines. The caller must reconcile the copied hireling identities with `RESC` hired flags and then commit all saved families together. `cNonHireFollowers` is derived from the NPC table and two party names, and `hirelingScrollPosition` is UI state; neither is stored here. Exact MM6 fees, quest-follower counts, profession effects, name localization and Dark Sacrifice behavior remain separate work.

Focused synthetic tests cover both full NPC copies, ability-use and opaque flags, distinct display names, active sacrifice, the shared RESC record codec, malformed/truncated/optional fields, invalid names/professions/timers, valid-CRC late failure before assignment, and wrong-title/corrupt-container rejection. The party adapter itself still needs a test with an initialized MM6 runtime and F5 hire/save/quit/relaunch/dismiss/sacrifice checks. `MM6KnownSaveFields` and `SaveLoad.cpp` were not changed; a later manifest revision must include required `HIRE`.
