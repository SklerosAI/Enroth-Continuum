# MM6 `.ec6` core party and character fields — F4 offline progress

Status: **bounded `PART` v1 / `CHAR` v2 codec and staging adapter, 2026-11-06; incomplete save, not wired to the game menu**.

The new `MM6CoreSaveFields` codec adds two required sections inside the existing title-tagged, CRC-checked `.ec6` envelope. Each section has its own version byte and strict length/count validation. `PART` stores gold, food, bank gold, playing-time ticks, three finite position coordinates, view yaw/pitch and active-character index. `CHAR` stores exactly four names (1–63 bytes without control bytes), sex, an MM6 class ID in 0–17, a vanilla face ID in 0–11, voice ID, level, experience, HP/SP, skill points, seven base stats, 31 MM6 skill values and 99 spell-known flags. Skill slot 30 maps to the current runtime's `SKILL_LEARNING`, following the MM6 creation path; values with Grandmaster or conflicting mastery bits are rejected. The 99 spell flags are packed into 13 bytes with zero padding required.

`CHAR` v2 appends seven signed 32-bit stat bonuses, signed 16-bit AC/level/age modifiers, a signed 32-bit birth year bounded to 0–10,000 and seven one-time pure-stat-potion flags per character. The potion flags occupy one byte with its unused high bit required zero. These are direct current-runtime `Character` fields consumed by derived stats, event variables and the pure-stat potion limit. `captureCharacterModifiers()` reads them from a real `Character`; `stageCharacterModifiers()` returns a validated, detached copy under an explicit MM6 title. The core party capture and stage paths call these helpers for all four characters. Earlier offline `CHAR` v1 samples are superseded; no live `.ec6` slots exist. The meaning and bounds of MM6 event modifiers still need gameplay proof.

`decodeCoreSections` validates both payloads into a temporary value. `loadCoreFieldsBeforeMutation` decodes and checks the entire container before assigning that value to its destination. The runtime adapter checks the game title, captures these fields from a `Party`, and `stageCoreParty` applies a validated container to a **copy** of the live party; it returns the staged copy without changing the caller's party. No SaveLoad or UI path calls this adapter yet. This ordering is the foundation for a later all-family load transaction, not a complete transaction by itself.

Offline evidence: the arm64 MM6, OpenEnroth and integrated unit targets built. Four focused core tests passed, including nonzero character modifier capture/stage on a detached `Character`, a four-character `CHAR` v2 round trip, padding/version rejection, wrong-title rejection and malformed-field no-mutation checks. Fifteen adjacent known-save, world-save and atomic-file tests also passed. This verifies preservation of current runtime fields, not native MM6 rule semantics. No MM6 game or original installation was opened.

**Completeness lock:** This core payload still omits private attack/health/mana bonus bytes, quick spell, spellbook page, beacons, prior face/voice and other Character state. Other bounded `.ec6` sections now cover condition times, resistance channels, buffs, inventory/equipment, quest/event/award bits, hirelings, timers, overlays and 67 map deltas, but the whole save still lacks shops, generated-artifact flags and more state listed in the [whole-save field register](MM6_SAVE_FIELD_REGISTER_F2.md). Live SaveLoad and the game menu remain guarded. Further F4 work must finish and test every required section, validate the whole save against a complete field manifest, and only then commit a staged runtime snapshot. F5 must verify graphical save/quit/relaunch/load and MM7 isolation.
