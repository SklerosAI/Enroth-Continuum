# MM6 action-observation stability at save commit — F4

Status, 2026-11-06: **source audit and commit-boundary blocker; no live SaveLoad route**. The MM6-only scoped new-game save has an idle-action observation but no mechanism that keeps all observed owners stable through a real map entry or restores them after failure.

## Current call order and evidence

1. `saveNewGameMM6ScopedForTest()` checks the live MM6 title and owner pointers, captures spell/target/turn/rest/GUI/movement/delayed-enchant activity, and rejects a non-idle `HELD` cursor plan. It then constructs the private map source, captures a fresh known-field seed and calls `runScopedFirstMapEntryForTest()`.
2. `prepareOfflineNewGameSession()` reads and validates the 67 default deltas and their bases, seeds detached CHST, encodes the known sections and stages a detached session. The scoped wrapper's concrete readers are synchronous archive/file reads and an item-table predicate. There is no explicit `MessageLoopWithWait()` or GUI dispatch in that wrapper before the write. This describes the present test path; it is not a lock or a contract for a future production caller.
3. `runScopedFirstMapEntryForTest()` snapshots the prior disk slot, writes the new `.ec6`, swaps the default-delta cache and CHST, then invokes a caller-supplied `FirstMapEntryProbe`. On a throw it restores the cache, CHST and primary/backup bytes only. The API expressly forbids the probe from mutating unrelated process globals, but cannot enforce that. It does not snapshot the GUI message queues, movement queue, spell queue, rest UI, turn engine, event state or active world.
4. `Game::gameLoop()` polls platform messages, generates keyboard actions, processes GUI messages and advances simulation as separate steps. `GUIMessageQueue` has current and next-frame queues; spell casting runs after the queue swap. `EngineControlState` prevents its game and control threads from running in parallel, but `EngineControlComponent::swapBuffers()` yields to the control thread and can run a game routine. A map-entry probe that renders or pumps events can therefore cross an execution boundary after the durable file was written. The current test probe is bounded; a future full-world callback is not.

## Why a second read is insufficient

Rechecking the same booleans immediately before `writeAtomicSaveFile()` would catch an action introduced during preflight, but it cannot reserve those owners through a callback that loads and renders a map. Rechecking after the callback would detect a change only after the disk and process owners have been published, while their action queues and UI effects are outside the rollback snapshot. An epoch counter has the same detect-without-recovery limitation. Read-only observation cannot by itself make this a failure-atomic all-owner transaction.

## Smallest prerequisite

Add a coordinator-owned, game-thread save/entry safe point before opening normal MM6 SaveLoad. It must either prevent GUI, keyboard, spell, turn, rest and event producers from running until the file and all process owners are committed, including through nested `Present`/event processing, **or** stage and no-throw restore every action owner and side effect that may run during the callback. The first option also needs an enforced no-reentry rule for map entry and a defined moment to resume input. The second option requires a complete action/UI/world rollback contract not present today. A test should inject a queued next-frame spell or movement action during preflight and a late map-entry failure, then prove exact disk, cache, CHST and action-owner state, plus an MM7 control. The current guards stay closed until that proof and full save–quit–reload verification exist.
