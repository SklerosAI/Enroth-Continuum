Neither establishes the exact original archive bytes or F5 audiovisual behavior. Exact per-entry names and candidate frame identities remain in ignored `local-game-data/mm6/`.

## Evidence and method

The pinned [`mmarch` VID reader](https://github.com/might-and-magic/mmarch/blob/fc104f2a7d8b170ed67bc05b9bfac5d0bb9a60b8/mmarch-rust/src/vid.rs) and [SND reader](https://github.com/might-and-magic/mmarch/blob/fc104f2a7d8b170ed67bc05b9bfac5d0bb9a60b8/mmarch-rust/src/snd.rs) provide independent source-level schemas. `scripts/mm6_probe_media_schema_leads.py` read only the ignored F1 `.entries` indexes, extracted PNG headers, and extracted `dpft.bin`; it wrote exact candidate names and records to ignored `local-game-data/mm6/research-2026-11-05/media-schema-leads-private.json`. It printed aggregate counts only. The current C++ readers and media consumers were inspected without running them.

## House-movie descriptor lead

The pinned [GrayFace MMExtension `Game.HouseMovies` declaration](https://github.com/GrayFace/MMExtension/blob/9d73c0ff0482bd231ea522f752f4fe9b26640925/Scripts/Structs/00%20structs.lua#L531) places an MM6 candidate array at virtual address `0x4BE888`, **119 entries**. Its [`HouseMovie` structure](https://github.com/GrayFace/MMExtension/blob/9d73c0ff0482bd231ea522f752f4fe9b26640925/Scripts/Structs/01%20common%20structs.lua#L1843-L1855) is **16 bytes**: filename pointer, background, NPC picture, house type and sound group. The retained `2devents.txt` room IDs fit within that candidate range. Current C++ instead uses inherited MM7 descriptors whose names do not match the retained MM6 video index.

This is a **version-sensitive process-memory locator**, not a verified file offset, original MM6 descriptor value or proof that every room triggers a video. At F3, map the exact executable's PE sections, validate the 119 × 16-byte span and pointer targets, join room IDs and video names privately, and account for absent/reused IDs and event conditions. The separate [executable locator packet](MM6_EXECUTABLE_TABLE_LOCATORS_F2.md) owns the wider PE preflight.

## Consequences for the MM6 implementation gate

1. Preserve the present 44-byte VID and 52-byte SND readers as *candidate-compatible* until F3 checks actual owner bytes. Prioritize MM6-specific extensionless video lookup and trailer/end-of-payload handling if the raw archive confirms them. Do not infer media decoder success from `.smk` or `.wav` extraction suffixes.
2. In F3, compare original archive directory names/counts, offsets, optional trailer, stored/unpacked lengths and representative payload signatures with the retained indexes. Keep exact names, hashes, samples and discrepancies in ignored private evidence. Revisit the source hypothesis if the original files differ.
3. Resolve the twelve candidate icon families, frame selection, voices and the 119-entry house descriptors against the exact game and retained tables before freezing F4 title-specific data. Do not fill gaps with MM7 names or let private custom portraits mask vanilla failures.
4. F5 still requires on-screen inspection of character creation and animated portraits, houses, opening/loss/ending movies, and audible samples in real UI/combat/event paths. Directory compatibility and offline extraction are insufficient for playback acceptance.
