# MM6 offline implementation build graph (draft)

Status: **[F3 gate accepted](MM6_F3_GATE_REVIEW.md); F4 offline implementation in progress, 2026-11-06**. This graph turns the [MM6 implementation checklist](MM6_IMPLEMENTATION_CHECKLIST.md) and focused packets into ordered code seams for the full offline MM6 build. The installed MM7 app, MM7 source worktree and its saves remain the protected control case; MM8 remains a separate reserved title.

The implementation should use the retained ignored reference set and private F3 reconciliation report. A module is ready for integration only when its active MM6 IDs/records have a typed path, malformed/unknown handling, a title-isolation check and a focused offline scenario. A title screen, successful archive parse or compile does not satisfy F4.

The ordering is a dependency graph, not eight mandatory serial coding teams. Resource readers and title IDs unblock world, rules and presentation work in parallel; event execution needs the MM6 model and world state; `.ec6` needs stable runtime fields; the integrated scenario harness is the final offline join. Use separate agent-owned branches/files for concurrent implementation, with one integrator owning shared dispatch and the checklist. Do not merge a half-implemented MM6 path into the MM7 runtime or install a new Atlas helper during an intermediate seam.

The [item-effect seams](MM6_ITEM_EFFECT_SEAMS_F2.md) require an MM6 read-window ID policy and direct-use dispatch before the item/action scenarios can pass. The 164-row triage is an evidence queue, not 164 verified effects; F3 reconciles exact roles before F4 fixtures lock them.

The [monster-effect seams](MM6_MONSTER_EFFECT_SEAMS_F2.md) require title-specific gender and multi-target selection, weapon-break eligibility, Energy/resistance and fixed-drop policy. Test each against the F3-reconciled rules; the current source/guide mismatches alone do not supply original outcome formulas.

The [late item-guide packet](MM6_ITEM_GUIDE_CLOSURE_F2.md) groups held-item event signatures; parse all affected map scripts before asserting those item gates work. The [six-table role packet](MM6_UNLOADED_TABLE_ROLES_F2.md) requires separate MM6 BTB dialogue, weekday profession news and item-combination consumers, plus F3 decisions on the other three files. The [media-schema packet](MM6_MEDIA_SCHEMA_LEADS_F2.md) narrows likely VID/SND directory widths, and the [trigger map](MM6_MEDIA_TRIGGER_MAP_F2.md) identifies map music, event sound, house/movie and spell-cue joins. F4 must follow F3-confirmed extensionless lookup, room descriptors, payload bounds, codecs and vanilla portrait selection. Candidate PNG dimensions and static sound-ID matches do not substitute for seen/heard F5 checks.

The [full manual/card review](MM6_MANUAL_CARD_FULL_REVIEW_F2.md) adds `Y` yell, item-in-hand and target shortcuts, NPC social/reputation choices, option controls and autosave ordering to the MM6 input, service and persistence scenarios. F3 must adjudicate conflicting mastery/XP/spell prose before F4 uses a numeric rule; F5 must exercise controls and visible state rather than infer them from a screen render.

The [extra-STR role packet](MM6_UNLISTED_STR_ROLES_F2.md) keeps nine unlisted string files and five extra event partners separate from the 68 active listed/global EVT baseline. F4 parses and routes only F3-proven active extras; opening, victory and loss text need title-specific flow if the original uses them. F5 checks these outcomes and save/reload without borrowing MM7's ending path.

The [NWC guide review](MM6_NWC_GUIDE_FULL_REVIEW_F2.md) adds 14 matching numeric potion claims, four dungeon walkthrough scenario families and limited Sword/Dagger mastery corroboration. The F3 [content packet](MM6_F3_CONTENT_RECONCILIATION.md) confirms 348 original members byte for byte. ## F3 source lock for F4

The [F3 gate review](MM6_F3_GATE_REVIEW.md) resolves original archive identity and checked schema boundaries or names a specific ambiguity with a conservative representation and F4/F5 check. The source SHA and private F2 report hashes come from `scripts/mm6_f2_freeze_manifest.py`; `scripts/mm6_f3_identity_preflight.py` was only one component of F3. F4 uses the corrected private PE v2 join and retained reference set; exact original bytes, per-ID ledgers and screenshots remain ignored locally. No F4 module is accepted solely because the F3 source gate passed.
