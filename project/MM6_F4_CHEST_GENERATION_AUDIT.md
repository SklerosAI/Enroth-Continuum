# MM6 F4 chest random-item generation audit

Status: **live MM6 chest generation remains blocked before mutation** (2026-11-06). After the initial retained-data audit, a bounded read-only trace of the owner-local executable matched the accepted F3 SHA-256 identity before disassembly. No game was launched. Exact disassembly and data locators remain in the ignored private companion.

## Established inputs and current call

The F3-backed 67-map known-save check found 1,223 nonempty fixed chest item slots: 280 positive template IDs and **943 negative random-item markers**, all within the six MM6 values `-1` through `-6`. The map validator accepts those six values as chest markers only; it does not generate items or prove the following 280 chest grid/tail bytes. Ground objects reject negative item IDs. MM6 `items.txt` has IDs 0–580; `MM6ItemTable::InitializeMm6` loads item weights for IDs 1–399 from `rnditems.txt` and three treasure-level enchantment chance rows, plus standard and special enchantment tables. `mapstats.txt` has a title-specific map treasure-level column. These are parsed inputs, not a verified generation algorithm.

Previously `Engine::_461103_load_level_sub()` called `GenerateItemsInChest()` without a title check after map loading. That shared function recognizes the negative IDs, remaps marker and map treasure levels through a fixed inherited matrix, optionally generates an artifact at the remapped top level, otherwise rolls 1–5 attempts per marker and chooses nothing, gold or an item by inherited thresholds. It mutates chest inventory, consumes the global RNG and can touch artifact state. Later `Chest::PlaceItems` uses the inherited chest table and `Item::postGenerate(ITEM_SOURCE_CHEST)` to lay out and finish items. Thus a successful MM6 map decode does not imply its chests have MM6 contents.

## New primary executable findings

The MM6 generator walks 20 fixed chests with a 4,204-byte stride and 140 item records per chest. It consumes one RNG draw before scanning any marker. A marker then rolls 1–5 attempts and remaps its tier with a **different MM6 7 × 7 table**. The first attempt uses the saved probability from the generator entry or the last additional attempt of an earlier marker; only additional attempts draw a fresh probability. Each selects nothing below 20%, gold from 20% to below 60%, or an item from 60% upward. The gold branches match the six small/medium/large amount bands already present in `Item::generateGold`. A top-tier branch calls a separate MM6 artifact picker that scans owned IDs **400–429** in party inventory, but its candidate loop extends through **430**. Retained `items.txt` names 430 “Leather Pouch,” so the anomalous extra candidate needs a deliberate original-behavior policy before porting. These findings establish the generator's outer control flow, not the complete item and placement transaction.

The exact remap pairs for the retained marker band are captured as a **detached**, bounds-checked `mm6::chestTreasureLevelRangeForMarker` rule with focused native tests. It does not run from the live load path. The original MM6 table has a seventh row that always selects artifact tier 7, although none of the 943 retained markers use `-7`. All 67 retained `mapstats.txt` rows carry zero-based map treasure level 6. The helper still preserves all seven map columns for altered maps. In particular, tier-4/map-level-1 maps to 2–3, tier-5/map-level-0 maps to 2–3, and tier-6/map-level-0 maps to 3–3; inherited MM7 remapping differs in those cells.

The MM6 random-item picker searches weighted regular templates **1–399**, then handles potion, wand and enchantment branches. At treasure tier 6 it also has a separate artifact trial over a 30-ID MM6 band with a 5% roll and a hard cap of 13 generated artifacts. This is distinct from the direct tier-7 artifact picker. The original chest placement entry shuffles the chest area using masked 8-bit RNG samples, then calls fit and placement helpers for occupied item records. That identifies the placement call chain, but its item finalization, grid encoding and full/failure behavior are not yet reconciled with the current `ChestInventory` and `.ec6` persistence model.

### Bounded MM6 random-item picker contract

A branch-complete read-only pass over the original picker established its `RANDOM_ITEM_ANY` base-ID order. Its 15-bit RNG advances a 32-bit state with the original multiplier and addend. Every ANY call draws an artifact candidate from 30 IDs, even at tiers 1–5. Only tier 6 then draws a 0–99 chance: below 5, an ungenerated candidate under the fixed 13-artifact cap is marked generated and returned as ID 400–429. Other outcomes draw a zero-based remainder against the sum of 399 regular template weights. Remainder zero returns item **1** directly, even when its weight is zero; positive remainders scan IDs 1–399 until cumulative weight reaches the remainder. That differs from the inherited MM7 selector's `+1` weighted roll. The retained six weight-column sums are 437, 827, 959, 970, 928 and 805. Item 1 has zero weight at tiers 4–6, making the zero-remainder branch observable with those tables.

The new `mm6::pickChestBaseItemId` is a **detached** preflighted model of this ID/artifact stage. It takes caller-owned 399 weights, 30 artifact flags and an RNG seed; returns the selected ID, staged flags, next RNG state and draw count; and rejects foreign titles, invalid tiers, empty/negative/overflowing weights and nonbinary flags before any result. Seeded native tests exercise the zero-remainder quirk, a later weighted ID, a tier-6 artifact, duplicate and cap fallback, and MM7 isolation. It does not construct an `Item` or run from the live chest path.

After base-ID selection, the original picker sets identification from the selected template, then routes type codes 0–2 through weapon special-enchantment chance, 3–11 through standard-or-special equipment chance, 12 through a wand charge draw, and other types straight to return. The weighted special-enchantment path filters level codes by treasure tier, sums type-specific chances and draws again; the standard path rolls an attribute and strength. The retained enchantment-chance rows are parsed by `MM6ItemTable`, but the complete 28-byte field layout, special-table eligibility, wand-charge base and later chest placement/finalization need native model and save-stage reconciliation. The picker contains no potion-power write; MM7 `Item::postGenerate` does, so calling it for MM6 requires separate original-placement proof. Requested-type modes are outside the chest ANY call and remain separate. The ignored private trace records branch addresses and per-draw order without publishing executable bytes.

## Proven mismatch and missing contract

- The inherited artifact picker and level-six random-item branch use `allSpawnableArtifacts()` and `Party::isArtifactGenerated` in the MM7 ID band **500–528**. Retained MM6 item roles put **message scrolls** in that band; MM6 artifacts/relics occupy **400–429**. The inherited artifact result is therefore title-wrong, irrespective of whether a particular roll occurs in a short test.
- The inherited remap matrix differs from MM6 for several marker/map-level pairs. `isRandomItem()` also accepts `-7`, while the retained MM6 map set and bounded save validator establish only `-1` through `-6` as active data. A separate seventh remap row exists in the original executable, but its live map use and persistence remain unproved.
- The outer RNG order, attempt count, thresholds and gold dice are located in the MM6 executable, and the ANY base-ID/artifact stage is detached and tested. Its later item field branches and nested enchantment draws are mapped but not implemented as an MM6 `Item` transaction. The placement fit, finalization and grid encoding still need the same treatment.
- The retained guide describes broad treasure and enchantment families but conflicts with a level-six weapon chance cell. It cannot settle the executable rule. The inherited chest placement uses a hard-coded 9 × 9 chest table, a global RNG shuffle and `postGenerate`; the MM6 280-byte chest grid/tail remains uninterpreted. Random results must also survive map reset and `.ec6` save/reload without regeneration or losing original marker state.

## Required title-specific boundary and unlock sequence

The `mm6::generateChestItemsForTitle` boundary runs at `_461103_load_level_sub` before inherited chest/RNG/artifact mutation. It throws for MM6 and unknown titles, while MM7 still calls `GenerateItemsInChest()`. This is **unconditional**: every MM6 level load reaching this call fails, including maps with no random markers. A marker-free skip would omit the original function's entry RNG draw and therefore needs an explicit title-specific policy and seeded proof. The focused native tests check the MM6 block, MM7 selection and divergent MM6 remap cells. A replacement should first validate all 20 chest containers, marker IDs, zero-based map treasure level, MM6 item-table rows and capacity as one transaction. It must then reproduce the original outer draws and all nested item/artifact draws, item field writes, MM6 chest grid placement and deterministic commit/persistence.

Unlock evidence is an MM6 `Item` transaction for all picker type/enchantment branches and placement helpers, reconciled with retained `rnditems.txt`, `items.txt`, chest grid/tail bytes, map reset and the guide disagreement. Run seeded synthetic and retained-data cases for all six active markers and all map levels, including a full chest, artifact roll, failed placement and exact RNG position; then inspect chest contents and save–quit–relaunch–load in F5. Until then, leave the live call guarded. See the [map item validation](MM6_EC6_MAP_FIELDS_F4.md) and [item guide audit](MM6_ITEM_MONSTER_GUIDE_CLAIMS_F2.md).
