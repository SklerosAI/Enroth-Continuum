# MM6 F4 Outdoor Border Trace

The [source packet](../project/MM6_F4_OUTDOOR_BORDER_TRACE.md) records a bounded original-MM6 border-route trace. Exact executable offsets and retained map names remain in ignored local evidence.

Original MM6 derives the neighbor from a five-column, three-row outdoor filename grid and out-of-bounds party coordinates. The accepted 15 outdoor map entries cover that grid. A caller tests party state before showing travel, and failure clamps the party inside the map. Confirmation rechecks the neighbor, applies a five-day baseline reduced by hireling checks with a one-day floor, and wraps the crossed axes by one full map width to preserve edge offset. Both axes may change at a corner. This differs from the MM7 border table and named arrival-point path.

The original party-state bit meanings, exceptional permissions, confirm-state closure, corner behavior and native arrival sample remain open. A pure [detached calculator](../src/Engine/MM6/MM6OutdoorBorderTravel.h) now returns a bounded grid/arrival/time candidate but always refuses a live offer. It reads or mutates no Party/global state; four synthetic route checks and three transition-intercept checks passed **7/7** on the integration build. The current MM6 title guard remains, and cross-map autosave still requires a complete `.ec6` transaction or separately proved transition policy. The traced helper has no direct fog or underwater predicate; this does not resolve MM6 weather.

An earlier ignored focused checker passed the accepted executable hash, route-helper/caller/confirmation structure, retained grid and current title guard. The later C++ checks used a headless unit build; no live travel or graphical MM6 launch occurred.
