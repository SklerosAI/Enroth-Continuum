# MM6 recovery, rest and calendar save field — F4

Status: bounded current-runtime `.ec6` `RCVR` v3 field and copy-staging, 2026-11-06. This is an offline field seam; the partial known-save manifest requires `RCVR`, while SaveLoad remains guarded.

## Source, consumers and lifetime

| Runtime field | Consumer and lifetime | Decision |
| --- | --- | --- |
| Four `Character::timeToRecovery` durations | Action gating in `Party.cpp`, `Character.cpp`, `UIGame.cpp` and turn engine; can span a save | Store exact nonnegative ticks. |

## `RCVR` v3 contract

`MM6RecoverySaveFields.*` adds required section `RCVR` with an exact 588-byte v3 payload. It stores the former 572-byte v2 recovery/event payload plus signed 64-bit Armageddon timer ticks and signed 32-bit damage/force values. The earlier 100-byte prefix and 59 signed 64-bit event timestamps remain in counter, history and unknown-time order. All integers use little-endian encoding. Event ticks may be `-1` (expired), zero or positive up to 10,000 elapsed years; this is a storage bound, not a claim about MM6 script behavior. The decoder rejects a missing/optional/duplicate section, bad shape/version/reserved byte, wrong title or container CRC before destination assignment. There are no live `.ec6` slots, so the prior offline v1/v2 sample formats are intentionally superseded.

The clock anchor must equal `PART.playingTicks`. `validateRecoveryAgainstCore()` provides this cross-section check; `stageRecoveryParty()` independently requires the incoming party copy to already have the same playing clock. Thus whole-save staging must apply core state first and validate both sections before committing the copy. On a valid stage, regeneration, rest days, recovery, daily counts, the three Armageddon values and derived calendar cache change on a Party copy. It does not alter live global rest UI, turn queue, OS/frame clock or MM7 runtime.

`captureRecoveryFields()` and `stageRecoveryParty()` require an active MM6 engine title, no active turn-based mode, and `currentRestType == REST_NONE` with zero `remainingRestTime`. These guards are intentional until the turn queue and rest action state have a complete save contract. The playing-time anchor is a consistency check, not a second source of truth. The smaller `captureEventClocks()` and `stageEventClocks()` functions take an explicit MM6 title and `PartyTimeStruct`; they validate first and return values or a copy without touching global party state. They are unit-testable without constructing a live `Party`.

The earlier v2 focused C++ tests passed in the linked arm64 unit target. The changed v3 codec, runtime adapter and focused unit translation units syntax compiled with integrated arm64 flags; a standalone native v3 probe passed exact 588-byte round-trip, old-version rejection and valid-checksum invalid-timer rejection without destination mutation. Linked v3 unit and game tests remain for main integration. F5 must check real save/quit/relaunch/load at day rollover, after a short rest, with nonzero recovery and daily-use counts, plus rendered calendar, journal behavior and spell availability. Armageddon progress and persistence also require title-specific spell-effect proof. No MM6 game process was launched in this lane.
