# MM6 map-byte dispatch — F4 evidence boundary

Status: **storage and ordinary-operation candidate, no enabled runtime dispatch, 2026-11-06**. This audit used the F3-matched retained EVT and map reports and public source at fixed revisions. It did not reread the original installation or launch MM6. The 200-byte DDM/DLV section remains opaque in code.

## Operation and state decision

[MMExtension's command reference](https://grayface.github.io/mm/ext/ref/) describes `evt.Cmp` as *usually* `Variable >= Value` and gives an MM6 example that increments `MapVar0` until a comparison against four succeeds. It defines Add, Subtract and Set with signed 32-bit operands in `evt.lua`, but does not state MM6 map-byte overflow, underflow or write narrowing. The inherited [MM7 executor](../src/Engine/Evt/EvtVariables.cpp) saturates positive adds at 255, subtracts from a byte without an underflow guard and narrows Set to a byte. That implementation is a comparison target, **not MM6 evidence**. The MM6 command's target selector may also cause repeated map writes if it follows the inherited per-character loop; this must be checked before enabling a title-specific branch.

The current [MM6 variable guard](MM6_F4_VARIABLE_GUARD.md) therefore continues to reject IDs 105–204 at execution. A valid F4 dispatch needs a nonzero MM6 state source or executable-dispatch evidence for: (1) the byte offset for IDs 105, 179, 180 and 204; (2) Compare's relation and signedness; (3) Add overflow, Subtract underflow and Set outside 0–255; (4) whether a map variable operation happens once per event or once per selected character; and (5) the exact leave/re-enter, timed-reset and save/reload policy. A synthetic mutation can test our codec and bounds but cannot by itself prove the original game's rule. Keep all 200 bytes and the tail intact while these questions are open.
