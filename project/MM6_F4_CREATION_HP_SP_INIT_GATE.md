# MM6 creation HP/SP initialization gate — F4

Status, 2026-11-06: a read-only trace of the accepted F3-identity original executable strengthens the **Quick Start initial HP** formula and HP/SP assignment order. A bounded MM6-only final-refill ordering correction now runs after starting-item grants; the inherited MM7 order remains before those grants. This does not justify changing the provisional maximum formulas or enabling the original Quick Start route. No live SaveLoad path changed.

## Original Quick Start and current creation paths

The original Quick Start finalizer resets the four characters, applies their class/stat/skill fixture, generates or places starting items, then calculates maximum health and mana and stores each result as current HP/SP. The last step is after the random first item and skill-driven equipment, so current HP/SP depends on the final item and skill state. This is the finalizer's direct order, not proof that later first-map callbacks preserve these values.

The original health calculation's inspected call chain has actual Endurance, its parameter bonus, actual level, the class HP factor, health skill and item bonuses, the family HP base and the full-health bonus. It clamps the result to **at least 1** before writing current HP. That term shape and floor match the current MM6 branch of `Character::GetMaxHealth()` and its private F3 base/factor arrays. The original mana calculation is a separate class-dispatched function; the finalizer stores its result as current SP. The F3 report proves base/factor arrays and the class mana-attribute dispatch, but explicitly leaves runtime HP/SP formula and promotion retroactivity unresolved.

The current editable creation path calls `Character::ChangeClass()` for a selected MM6 starting class and fills HP/SP there. It allows stat and skill edits afterward. On accepted `UIMSG_PlayerCreationClickOK`, the creation screen first requires all points and four skills, then its finalizer generates a ring, grants skill-specific items/spells and identifies inventory. Before this correction it refilled HP/SP between the ring and the skill grants. The MM6 title branch now refills after the grants, following the original Quick Start finalizer's proved safe ordering; MM7 still refills before them. `Party::Reset()` and its provisional MM6 default composition also fill from the max methods. This is current-source evidence; it does not make the provisional default party the original Quick Start fixture or prove that original editable creation uses the identical finalizer.

## Why no formula correction is safe yet

The direct Quick Start HP chain matches the existing MM6 expression at the term level, so no distinct HP arithmetic fix is indicated. The original mana function has multiple class branches and nested actual-stat/age, item, skill and bonus helpers. A term-level comparison to the fork's `GetActualIntelligence()`, `GetActualPersonality()`, `GetParameterBonus()`, `GetSkillBonus()`, `GetItemsBonus()` and class-specific Meditation behavior is not yet complete. Neither the original finalizer nor the F3 report provides a nonzero post-entry character-sheet/save observation for all six families and promoted tiers. Changing SP or promotion arithmetic now could introduce a regression without a verified expected value.

The later [max-mana condition trace](MM6_F4_MAX_MANA_CONDITION_TRACE.md) closes all four outer class returns and corrects one nested actual-stat condition term. Remaining proof covers the original mana item and skill helpers, promoted levels, and an owner-local native Quick Start or created-party save after first-map entry. Explicitly test no-magic, single-stat and dual-stat classes, negative bonuses, equipment/Meditation, level modifiers and promotions. The original Quick Start fixture and random inventory have separate open gates in the [Quick Start audit](MM6_F4_QUICK_START_AUDIT.md).

The focused `MM6CreationVitals` test uses an item that changes both maximum values between the two stages: MM6 refills afterward, while MM7 retains the earlier values.
