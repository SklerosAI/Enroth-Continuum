# MM6 F4 New Game Autosave

The [first-map packet](../project/MM6_F4_NEW_GAME_AUTOSAVE.md) traces why `Game::loop()` reaches the MM6 `saveNewGame()` guard before its pending `oute3.odm` map can load, and records the offline `.ec6` autosave seam.

The [native v2 first-map candidate](../project/MM6_F4_V2_NEW_GAME_CANDIDATE.md) now composes the existing seed with explicit physical `INVR`, `HELD`, `SHOP` and `SCLK` owners, verifies raw item/cursor replay against the source Party, validates all 67 map bases and returns staged v2 bytes without mutation. A separate offline helper atomically writes only that prepared candidate to `autosave.ec6`. Synthetic linked tests passed **3/3**, including a matched plain item/cursor disk round trip and refusal of a visible starter item lacking native raw provenance. Current party creation does not attach `mm6RawRecord` to its grants; exact live raw capture and the full child/session commit remain open, so the normal New Game and SaveLoad guards stay closed.

`encodeOfflineNewGameAutosave()` replaces MAPS in an already detached known-field seed with 67 title-specific default archive deltas, derives the active CHST raw sidecar from the decoded first-map default delta, then validates the eighteen-section candidate and all 67 base/delta pairs before returning bytes. `writeOfflineNewGameAutosave()` passes those bytes to the native atomic writer at fixed `autosave.ec6` in an explicit MM6 profile. Three synthetic native tests cover nonzero first-map state, wrong-title and wrong-map rejection before reads, malformed final-delta failure before disk mutation, and semantic backup preflight/recovery. The route is offline only; `SaveLoad.cpp` still rejects MM6 before MM7 serialization.

The newer `prepareOfflineNewGameSession()` draws a port-specific chest seed once into a detached owner, builds the default-map candidate, and stages all represented Party/Character, world, visual, CHST and SCLK owners before returning bytes and owned copies. It requires fresh zero refresh clocks and no party-owned chest artifacts. `writeAndStageOfflineNewGameAutosave()` writes the fixed slot only after this preflight. The returned 67 map buffers are ready for a future `pMapDeltas` handoff, but neither helper assigns process globals. Synthetic tests include nonzero staged Party/NPC state and a final Party-adapter failure that preserves the old disk slot and live owners. The live guard remains closed.

`captureFirstMapKnownSeed()` now captures represented Party/NPC/timer/overlay fields with arrival placement on a detached Party copy. `writeAndPublishOfflineNewGameAutosave()` preflights, writes, then publishes the validated 67-map cache and CHST title owner through no-throw swaps. It retains the old values for `rollbackPublishedFirstMapCache()` if map entry fails. This handoff remains an offline helper; it has no Party/world commit or disk-slot rollback, and no MM6 SaveLoad call-site uses it yet.

The separate test-only `saveNewGameMM6ScopedForTest()` checks the current MM6 engine and uses the owner-local F3 manifest, loaded MM6 Games LOD and item table to call `runScopedFirstMapEntryForTest()`. The runner now finishes its bounded observer against the detached Party/map/CHST candidate **before** disk or process publication. The scoped wrapper then rechecks pending actions. A callback failure or new action leaves the prior slot/cache/CHST untouched; a writer failure retains the existing disk rollback path. The callback must not mutate other process globals. Normal `saveNewGame()` and all MM6 SaveLoad guards remain closed; real `DoPrepareWorld` is not yet a detached candidate.

The monitored `GameTests_MM6Save.cpp` exercises this wrapper with loaded private MM6 resources and an ignored F3 map source named by `ENROTH_MM6_MAP_RESEARCH_ROOT`. It writes only into a unique temporary native profile, checks first-map staged Party/cache/CHST state, then tests exact rollback of primary, backup and process cache/title owners after a callback failure. It skips when the private map source is absent. This does not call the full outdoor world loader.

The linked monitored private test passed 1/1 in 21.0 seconds with no focus change or on-screen window across 1,566 samples. The ignored log is `local-game-data/mm6/research-2026-11-05/F4_MM6_SAVE_HEADLESS_TEST_PRIVATE.log`. Full outdoor entry, broader world rollback and normal SaveLoad remain guarded.

A later dedicated `MM6ZSaveHeadless` test drives the real Main Menu → editable Create Party → `saveNewGame()` → `DoPrepareWorld` control flow. A test-only callback redirects the MM6 save to a unique temporary `.ec6` profile; it is absent in a normal user session, where the guard still rejects MM6. The first run exposed inherited MM7 starter books in the MM6 artifact range. After the title-specific creation grant was corrected, the test reached the first outdoor frame with actors and twenty chests, passing 1/1 under a no-window/no-focus monitor. The ordinary MM6 save route, rollback on a late real-world failure, quit/relaunch/load and campaign play remain gated. This supersedes the earlier statement above that no test had entered the full outdoor loader.

The [loaded-archive source](../src/Engine/MM6/MM6LoadedMapSource.h) now obtains all 67 map pairs directly from the MM6 Games archive and map table. It uses the existing bounded decoder for two known indoor checksum exceptions. A monitored private F3 comparison matched the 67 ordered names and decoded bases (1/1); the test-only New Game route then reached the first outdoor frame using only the loaded game archive for maps (1/1). A separate callback-failure test confirmed `saveNewGame()` restores its own MM6 map and placement fields; it does not cover later world-loader effects. The default guard and MM7 vendor-entry controls remain passing. Normal MM6 save/load remains closed.

The loaded-archive path now exposes `prepareNewGameMM6FromLoadedMaps()`: an owned, read-only candidate containing staged EC6 bytes/session and a detached outdoor geometry/terrain plan. The test-only writer publishes its already prepared session only after the pending-action and precommit-probe recheck, so invalid outdoor geometry rejects before disk/cache/CHST mutation and the archive/chest seed are not read twice. The new synthetic precommit regression and the other focused save checks passed in the integrated linked run (31/31). The detached outdoor plan is not a live world commit, and the normal SaveLoad guards stay closed.

Two separate hidden GameTest processes then shared one disposable owner-only temporary profile. New Game wrote its partial `.ec6` in the first process; the second selected and staged that persisted slot into fresh detached owners, validated the first-map plan and starter inventory, and confirmed no disk mutation. Both passed 1/1 without visible windows or focus change, and the profile was removed. This is a fresh-process persistence check for represented fields, not live `loadGame()`, complete owner serialization or a save–quit–relaunch–play acceptance check.

A further **test-only** fresh-process probe now publishes the staged represented Party, NPC, timer, overlay, map-cache and chest owners in an isolated GameTest process, then calls the real `DoPrepareWorld(true, 1)` under the explicit chest opt-in. It reaches the first outdoor map with actors and twenty chests and leaves the `.ec6` bytes unchanged. The rebuilt probe passed **1/1** with no visible window or focus change. It starts from the loaded MM6 NPC table because the save contains mutable NPC fields, not the static name pools needed by world initialization. This is a destructive test-process handoff, not a failure-atomic production `loadGame()` commit. Omitted owners, late-failure rollback, rendered output and normal save–quit–relaunch–play remain open.

The newer isolated reload probe then advances the timer, actor AI, queued turn/walk input and engine draw after that world entry. Two separate integrated monitored processes passed 1/1 each for the disposable New Game write and the fresh-process world/frame probe, with no visible window or focus change; the temporary profile was removed. This remains inside the GameTest party-creation parent loop, not production `loadGame()` or a complete `Game::gameLoop()` frame. The null renderer does not establish rendered pixels.

A subsequent focused rerun checks the two load-style skip gates across separate bounded frames: world update is skipped first, queued user input is held on the next frame, then turn/walk actions drain and move the Party on a third draw. The write and fresh-process reentry each passed 1/1 under the host monitor, with no visible window or focus change. The disposable profile was removed. At that checkpoint the actual `Game::gameLoop()` remained private to the guarded New Game/Load control flow; the newer test-only menu-route probe below supersedes this control-flow limit.

The test-only `stageOfflineSaveSlotForTest()` now reads a temporary native EC6 primary/backup pair into fresh, detached Party/NPC/timer/overlay owners. It selects a candidate only after the existing native slot preflight and `stageKnownSession()` validate all represented owner families, 67 map pairs, the typed active map, CHST raw sidecar/LCG and SCLK. The returned bytes, staged session and recovery-needed flag are independent of live globals; the helper never repairs disk. New synthetic cases cover nonzero stage, foreign title, late Party rejection, corrupt primary with intact backup, two corrupt copies and absent slot. The existing private headless GameTest also checks a real first-map slot read with the ignored F3 map source, MM7 rejection and read-only backup selection.

After integration, the linked `MM6NewGameSaveRuntime.*` native suite passed 13/13 in 13.94 seconds, including the two fresh disk-stage cases. The monitored private `MM6ZSaveHeadless.*` test passed 1/1 in 35.248 seconds. The host monitor observed 2,368 samples, no focus change, zero on-screen windows and the same front application before and after. Its ignored log is `local-game-data/mm6/research-2026-11-05/F4_MM6_DISK_STAGE_HEADLESS_PRIVATE.log`.

The [first-map world rollback audit](MM6-F4-First-Map-World-Rollback.md) classifies the outdoor and engine owners changed after the save callback. A bounded scratch owner now protects actor, sprite, chest and decoration collections under late synthetic failure; the outdoor object, Party, transition/events and resource/UI effects still need joined rollback before a full loader can be called atomically.

The seed is only the represented field set. The older byte-builder requires the caller to supply CHST state; the staged new-game helper draws one port-specific seed into a detached owner. Native resource identity, MM6-keyed commerce/bounty, beacon images/map identity, persistent event variables, the complete first-frame path and the final all-owner reload are not proved. `PART` v3 preserves fall-start Z; the offline builder requires the source-backed 340 position and fall-start Z before archive reads. The isolated fresh-process world-entry probe is not a normal `loadGame()`, all-owner rollback or rendered-state proof. Keep live first-map autosave guarded until a full `.ec6` capture, atomic write/recovery, quit/relaunch/load and rendered-state scenario succeeds.

The [child-process game-loop handoff audit](../project/MM6_F4_CHILD_PROCESS_GAME_LOOP_HANDOFF.md) traces the route: main-menu Load sets `MENU_LoadingProcInMainMenu`; `Game::loop()` enters private `gameLoop()`, which calls `loadGame()` before `DoPrepareWorld(true)` and the first frame. A new **test-only** MM6 QuickLoad and `loadGame()` callback followed that route from a fresh process using the partial v1 disposable slot. The separate writer and loader each passed 1/1 under a host monitor (131 and 51 samples, no focus change or on-screen window). The loader reached the first outdoor map, cleared the game-loop skip flags, processed turn/walk actions and left slot bytes unchanged. This supersedes the earlier statement that no restart probe entered actual `gameLoop()`; it does not prove production load, complete v2 staging or rendered pixels. Normal MM6 SaveLoad and the in-game slot list remain guarded. Native v2 structural file APIs exist, but raw v2 still lacks a complete live-session coordinator. A one-campaign-per-child MM6 runtime could let a failed world entry terminate without rolling back an older live session, but must redirect in-game load and return-to-menu actions to a fresh child; it does not excuse disk autosave safety or first-frame validation. Atlas MM6 Play remains unwired.
