# MM6 native v2 first-map autosave candidate

The offline `prepareOfflineRawNewGameAutosave()` seam builds a nineteen-section EC6 v2 candidate from the existing detached first-map `KnownSaveFields` seed and explicit MM6 physical `INVR`, `HELD`, `SHOP` and `SCLK` owners. It carries `PART`/`CHAR`, QEST/EFFT, metadata, RESC, RSTS, BUFF, HIRE, RCVR and CHST from the seed. It reads the 67 default map deltas, derives the decoded `oute3.ddm` CHST sidecar, encodes native v2 bytes and calls `stageRawTitleOwners()` to validate every map/base pair and referenced item. No live owner or disk slot changes during preparation.

The source Party is copied to the established New Sorpigal arrival pose and checked against the seed's core, quest/effect, resistance, buff, hireling, recovery and logical held fields. Its inventory is normalized from the inherited 126-slot capacity to MM6's 138 slots without changing source indices. Physical `INVR` is accepted only when projecting and recapturing that Party gives exactly the supplied raw bytes; unused raw record bytes remain authoritative. The cursor likewise must replay exactly against `pPickedItem`, including the 28-byte carrier. Unsupported potion/special/artifact unions, missing raw provenance, mismatched items, nonempty fresh `SHOP`/`SCLK`, inherited MM7 commerce/bounty state, beacons, observed indoor face overrides and prior artifact flags reject before encoding. The caller supplies the empty first-map physical shop owner explicitly.

`writeOfflineRawNewGameAutosave()` accepts only a prepared candidate whose staged fields re-encode to the same bytes and uses the native v2 atomic writer at `saves/autosave.ec6` in an explicit profile. The new synthetic linked arm64 tests passed **3/3**: exact unreferenced bytes and empty-cursor tail, a matched plain item and held cursor written/read as v2, mismatch/unsupported/no-provenance rejection, foreign title and nonempty shop rejection, and a tampered prepared candidate rejected without changing the disk slot. These tests did not inspect private MM6 files or enable SaveLoad.

**Remaining capture gap:** `UIPartyCreation.cpp` currently grants the starting ring through `generateItem()` and skill items through `inventory.add(Item(...))` or `grantMM6StartingSkillItem()`; those paths do not set `Item::mm6RawRecord`. No source-backed first-map adapter yet constructs native 28-byte records, physical grid/equipment indices, and the title-local cursor owner from that live creation state. The seam intentionally rejects that Party even when the visible item ID matches. The seed's NPC, timer/overlay and chest RNG fields are validated as save fields but still rely on their caller's capture/entropy source; the candidate does not prove a complete active-world or UI commit. The v2 child-process reload probe and production New Game/Load must remain gated until exact live capture and all-owner staging/publication are verified.
