# MM6 raw held cursor image plan

Status: **detached resource request only**. The v2 session stage now joins physical HELD with a detached Party item, but does not construct or publish a mouse image.

`Party::setHoldingItem()` first moves or drops any prior held item, then assigns `pPickedItem`, asks `Io::Mouse::SetCursorBitmapFromItemID()` to select the item-table `iconName`, and writes a pickup offset. `takeHoldingItem()` resets Party item, selects `MICON1`, and zeroes that offset (`src/Engine/Party.cpp`). `Io::Mouse::DrawPickedItem()` resolves the held item's icon through `assets->getIcon()` and draws it red when broken, green when unidentified, otherwise untinted (`src/Io/Mouse.cpp`). `DoPrepareWorld()` selects an icon for a nonempty Party item, but does not restore `pickedItemOffset` (`src/Engine/Engine.cpp`). These are live asset/UI operations; calling `setHoldingItem()` during load would also run its prior-item relocation side effect.

`stageRawCursorImagePlan()` takes the detached Party, authoritative `RawHeldCursorOwner`, caller-supplied MM6 item table and MM6 title. For a held item it requires the same ID and retained 28-byte record on Party, projects through the bounded item adapter, replays the Party item exactly to the physical record, and returns only the table icon name and draw tint. For an empty raw cursor it requires a canonical empty Party item and returns the `MICON1` arrow request with zero offset. It rejects wrong title, unready owner, stale Party state and unsupported item templates before any live mutation. Focused synthetic tests cover all three tint branches, both occupancy states and failure cases.

**The pickup offset for a held item is unresolved.** The raw v2 HELD section contains the physical item record, not `mouse->pickedItemOffset`; the new plan returns no offset for an occupied item rather than claiming zero matches the original view. The loader must define and verify a deterministic restored offset or extend the save contract before visual equivalence is claimed. Resource lookup is also pending: a nonempty template icon name is not proof that `assets->getIcon()` can load and render it. A future fresh-child transaction must resolve the icon, join Party/raw process cursor and mouse image, then publish them coherently before `gameLoop()` draws the first frame. Normal MM6 SaveLoad, the load menu and Atlas Play remain guarded.
