# MM6 bounded character inventory projection — F4 detached stage

Status, 2026-11-06: `MM6BoundedInventoryProjection.h` supersedes the earlier plain-only inventory stage. It admits source-typed plain/gold records and the separate source-backed standard-enchanted equipment view while preserving the exact 138-slot physical region. No live Party owner, normal SaveLoad route or full item transfer is opened.

`stageBoundedItem` chooses the [plain item adapter](MM6_F4_PLAIN_ITEM_PROJECTION.md) for zero-bonus records and the [standard equipment adapter](MM6_F4_STANDARD_ITEM_PROJECTION.md) when the bonus or strength word is nonzero. Both keep `ItemRecord28` authoritative, revalidate table type and reject unsupported unions. `stageBoundedInventory` then checks each positive grid/equipment word for a unique in-range referenced item, places it at its original runtime index, and requires exact rebuild of every grid and equipment word. Negative continuation cells, the final physical item slot, unreferenced item bytes and source item tails are retained. The source and original placement/type metadata are private to the projection object.

Capture allows backpack repositioning and each item's bounded mapped field changes, including a standard equipment bonus and strength edit. The old [plain-only packet](MM6_F4_PLAIN_INVENTORY_PROJECTION.md) remains as historical evidence of the initial stage and points here for the current API.

Update, 2026-11-07: capture now takes every item's 28 bytes from its `Item::mm6RawRecord` carrier instead of the record it was staged from, so an item can move between grid and equipment, change slot or record index, and arrive from another owner. A read-only trace of the accepted F3-matched executable (same SHA-256 as the F3 identity) backs each rule. The paperdoll handler and its generic equip helper copy all 28 cursor bytes into the first zero-ID record and write the one-based equipment slot into byte 24. A swap keeps the record index and returns the old item to the cursor with byte 24 cleared. Unequipping copies the record, byte 24 included, to the cursor and clears bytes 0–24 of the record. Backpack pickup copies 28 bytes to the cursor and clears 0–24, and backpack placement copies 28 cursor bytes into the chosen record. Capture therefore clears bytes 0–24 of every vacated referenced record, writes each moved or new item at its current index, rejects an item without a carrier, rejects a placement on an unreferenced record whose item number is nonzero, and rejects an equipped moved item whose byte 24 doesn't name its slot. Records reused and vacated again between two captures keep the earlier tail bytes 25–27, where the original would hold the last occupant's tail. Those bytes are never read before the next full 28-byte copy. Template type changes for unmoved items still reject. Removal paths other than backpack, paperdoll and item-event Subtract, such as consumption or sale, are assumed to clear the same 25 bytes and still need their own trace.

Focused bounded-inventory, plain/standard item and bonus-map unit checks passed **7/7**. Two monitored MM6 headless checks with the loaded private-backed item table passed **2/2** over 65 samples without a visible window or focus change: one stages a final-slot scroll with the actual icon footprint; the other stages equipped standard-bonus armor and captures a changed attribute and strength while preserving an opaque tail byte. These checks use synthetic item records and do not validate native nonzero saved-item bytes or gameplay effects.
