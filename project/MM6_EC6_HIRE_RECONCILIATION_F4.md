# MM6 HIRE/RESC identity reconciliation — F4 offline finding

Status: **bounded correspondence diagnostic; no strict cross-section rejection rule is justified yet** (2026-11-06).

The current source does not store a stable source NPC ID in either `Party::pHirelings[2]` copy. Ordinary hiring sets `NPC_HIRED` on the dialogue NPC and copies its `NPCData` into a party slot; subsequent ability use and name restoration can change the copy independently. `setNPCNamesOnLoad` rewrites table names from `pNPCUnicNames` and hireling names from separate party display strings. Event `VAR_NPCs2` can clear a table hired flag without clearing a party copy. `VAR_HiredNPCHasSpeciality` can clear table flags and party slots by profession, leaving display-name strings untouched. The current new-game path marks one table NPC hired with both party hireling slots empty, and `FlatHirelings::Prepare` treats such table-only flags as followers. Generated NPCs come from `pAdditionalNPC` rather than the 501-slot `RESC` table. These source paths are title-inherited and do not prove every path's MM6 gameplay reachability, but they disprove a universal HIRE/RESC equality invariant for the current runtime.

The ignored F3-matched retained MM6 `npcdata.txt` copy has 398 numeric rows. Aggregate duplicate checks found **five duplicate-name groups covering 13 rows**, including **one duplicate name + portrait + profession group covering three rows**. Exact IDs and names stay private. Even that three-field tuple cannot serve as a stable identity key. The F3 logical save manifest calls for two paid follower slots but contains no native MM6 whole-save sample or hireling source-ID mapping.

`inspectHirelingCorrespondence` validates each HIRE and RESC section's bounded fields, then reports for each occupied party slot how many active table rows have the same name, portrait and profession, and how many of those rows carry `NPC_HIRED`. It scans at most 2×501 entries, makes no global mutation and **does not reject** zero, one or multiple candidates. Zero may mean a generated/renamed hireling; a one-candidate row with a cleared flag may reflect an event mutation; multiple candidates are present in retained source content. Empty party slots can coexist with table-only quest followers.

The later save transaction should preserve both sections exactly and may log this diagnostic privately. Do not coerce flags or discard a party copy on load. A strict identity validator requires a title-specific stable source ID recorded at hire time, explicit generated-NPC provenance and verified event/quest-follower rules, followed by F5 hire/dismiss/save/relaunch observations. `cNonHireFollowers` can be recomputed after a fully staged load, but duplicate-name behavior still needs review before making that a commit step.

## MM6 follower roster bounds

The inherited `FlatHirelings` implementation stores a table row plus two in a signed one-byte slot and asserts that the value is below 256. The retained F3-matched MM6 NPC table has 398 populated rows and an active upper bound of 399, so a hired table-only follower in a high row could not be represented by that path. The MM6-specific roster now uses a checked 16-bit index for all 501 possible table slots plus two party slots. `collectFollowerIndices` preserves the inherited order and exact case-sensitive name exclusion, rejects an active count outside 0–501 and an unnamed hired row, and has no write side effects. The MM7/MM8 roster path retains its original storage and behavior.

This change only makes table-row addressing safe. It does not add a stable source ID to either party hireling copy, resolve duplicate names, prove that every high table row can become a follower, or connect HIRE/RESC to live MM6 save/load. The normal and high-row cases are covered by synthetic offline tests; F5 hire/dismiss and save/relaunch observations remain required.

## NPC ID lookup bounds

The inherited `getNPCData` warned on table IDs beyond its 501-slot array but still formed the invalid pointer; generated IDs beyond its 100-slot array had no check. Negative follower IDs passed through `std::abs(int)`, which cannot represent the magnitude of the minimum signed integer. MM6 now resolves these three namespaces before pointer arithmetic: table IDs 0–500, generated IDs 5000–5099, and negative one-based positions in the current flattened roster. Invalid IDs throw `std::out_of_range`; `getNPCType` uses the same checked resolution for MM6. The MM7/MM8 branches are unchanged. Synthetic tests cover upper table and generated rows, the 503-entry maximum roster, each out-of-range boundary, and the minimum signed integer.

This is an address safety check, not a claim that every reserved table or generated slot is populated or reachable through MM6 events. The duplicate-name dismissal paths in `NPCTopics.cpp` and `UIDialogue.cpp` still clear every same-name hired table flag. An on-screen party copy has no stable source table ID, and retained records include duplicate name/portrait/profession tuples; changing that behavior safely needs provenance or F5 observations. No name-based coercion was added.

Focused synthetic tests cover table-only quest followers, unmatched/generated party copies, a table flag cleared after copying, three identical candidate tuples, and malformed HIRE/RESC input rejection. No original installation was reread or partial MM6 process launched.
