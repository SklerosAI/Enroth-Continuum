# MM6 child-process game-loop handoff audit

Status: source audit begun at integration `4cce4cafd`, updated after the v2 disk boundary, detached Party inventory stage and a monitored test-only Main Menu Load transition. No production guard was opened. An earlier disposable GameTest reentered the first outdoor map from an `.ec6` in a second process and exercised the two frame-skip gates and a movement/draw step, but remained in party creation. The newer probe below enters the actual `Game::loop()`/`gameLoop()` control route.

## The actual control route

`Game::run()` drives its menu FSM, then `Game::loop()` ([Game.cpp](../src/Application/Game.cpp)). The main-menu load state sets `_pendingLoadFileName` and `MENU_LoadingProcInMainMenu` ([MainMenuState.cpp](../src/Application/GameStates/MainMenuState.cpp), [LoadSlotState.cpp](../src/Application/GameStates/LoadSlotState.cpp)). `Game::loop()` calls private `Game::gameLoop()` on that menu value. `gameLoop()` calls `loadGame()` **before** portraits, `DoPrepareWorld(true, 1)`, the first input skip and the first frame. `loadGame()` still rejects MM6 at its first branch when the test-only callback is absent ([SaveLoad.cpp](../src/Engine/SaveLoad.cpp)). Thus the main-menu route is the smallest future route into the actual loop; no external call to the private method is needed.

The New Game route instead leaves `PartyCreationUI_Loop()`, sets the `oute3.odm` transition, calls `saveNewGame()`, then calls `gameLoop()` with `bLoading == false`. The production MM6 `saveNewGame()` guard rejects before map entry. The GameTest override only demonstrates this route in a disposable process; it is never a user-session writer. `DoPrepareWorld()` then mutates map, resource, event, actor, chest, UI and audio state ([Engine.cpp](../src/Engine/Engine.cpp)); the MM6 chest map route is additionally behind a test-only scoped opt-in ([MM6ChestMapLoadRoute.h](../src/Engine/MM6/MM6ChestMapLoadRoute.h)).

### Verified control-route probe

`MM6ZSaveHeadless.DISABLED_RestartSlotThroughMainMenuGameLoop` uses the partial **v1** `autosave.ec6` written by a separate disposable New Game process. In the fresh reader process it explicitly installs an MM6-only test callback for the Main Menu QuickLoad event and another for `loadGame()`. The event follows `MainMenuState` → `MENU_LoadingProcInMainMenu` → `Game::loop()` → `Game::gameLoop()` → `loadGame()`. The load callback read-only stages the v1 slot, validates its first-outdoor plan, publishes only its represented owners inside the disposable process, and holds the test-only chest opt-in through `DoPrepareWorld(true)`. The game loop itself then clears the world-update and input-skip flags and processes queued turn/walk actions; the test checks outdoor map identity, twenty chests, movement and unchanged slot bytes. Both overrides are cleared before the test ends. The null renderer proves no pixels.

The writer and loader each passed **1/1** in separate monitored processes with exits 0. The host recorded 131 and 51 samples respectively, no focus change and zero on-screen windows. This establishes the real control branch and one continuing gameplay step under a test-only v1 handoff. It does **not** establish a complete v2 session, production `loadGame()`, failure-safe world publication, a rendered frame or campaign play. The normal MM6 guards and empty MM6 load menu remain in effect.

## A single-campaign child process

The Atlas already starts MM7 as a separate `Process` with `--game`, `--data-path` and `--user-path` ([AtlasApp.swift](../launcher/AtlasApp.swift)). The title-locked MM6 helper and default MM6 profile path exist ([OpenEnrothOptions.cpp](../src/Bin/OpenEnroth/OpenEnrothOptions.cpp), [PathResolver.cpp](../src/Application/Startup/PathResolver.cpp)), but Atlas has no MM6 Play action. A future accepted MM6 helper can run in its own process and profile. First use the existing in-child main-menu load route; an optional direct-launch slot argument can follow after that route passes. No installed Atlas or profile should change before the play/save gate.

Process isolation **can remove rollback to a previously playable in-memory session** if each child owns exactly one campaign: load/new game starts from a fresh child; any staging, publication, `DoPrepareWorld` or first-frame failure ends that child; returning to menu or loading another slot cannot reuse a dirty child. Atlas then launches a new child for the next campaign. This is a narrower contract than same-process atomic publication, and it must be enforced. Today [GameMenu.cpp](../src/Application/GameMenu.cpp) and `quickLoadGame()` in [SaveLoad.cpp](../src/Engine/SaveLoad.cpp) call `loadGame()` from an active session, so those actions must request a fresh child or remain unavailable for MM6. `Game::run()` can also return to its main menu in the same process; a single-campaign mode must exit instead of accepting another New Game/Load there.

Process isolation does **not** remove complete format/resource validation, a coherent owner publication order, checked map/chest/renderer/UI construction, a successful frame, or durable save safety. A child could otherwise enter play with missing state rather than fail. It also does not roll back a disk autosave written before a failed New Game world entry. The New Game path must either publish its complete v2 autosave only after world/first-frame acceptance, or retain a separate atomic disk rollback/recovery contract. The existing guarded `saveNewGame()` runs before `DoPrepareWorld`, so this ordering must be made explicit. MM7 keeps its own title-locked helper, data and profile, with no MM6 fallback to MM7 serializers.

## Smallest staged patch sequence

1. Finish and version the complete v2 manifest, then build one title-local detached load coordinator that validates the selected primary/backup and all MM6 resource references without process mutation. A future process-start candidate must be independent of stale globals.
2. Connect the existing native v2 writer/selector/lister to the **complete** format validator; prove corrupt-primary/valid-backup selection and malformed v2 rejection before mutation. Wire the MM6 menu to the fully validated read-only listing.
3. Add a fresh-child-only MM6 `loadGame()` branch, keeping the current guard as the fallback until the branch passes. Publish the fully staged Party, raw inventory/shop/cursor, NPC, timer/overlays, map/chest and event/action owners, then set `MENU_LoadingProcInMainMenu`'s saved-map transition and `ENGINE_LOADING_SAVEGAME | ENGINE_SKIP_NEXT_WORLD_UPDATE`. Let `gameLoop()` call `DoPrepareWorld(true)` and set its input skip. Abort the child on any failure before it becomes interactive.
4. Repeat the verified test-only `Game::loop()`/`gameLoop()` control route with a **complete v2 production candidate**, including world entry, both skip gates, movement, save-file immutability and exit. Then verify a hidden rendered frame and the Atlas child lifecycle without changing MM7. Only then connect MM6 Play and a production New Game writer with a complete durable autosave contract.

The raw v2 slot can be written and structurally listed by the native helper, but it cannot be treated as a complete playable campaign or listed by the MM6 menu. The verified GameTest route deliberately supplies a v1 partial slot and a callback; it is a control-flow probe, not a substitute for the missing production coordinator.
