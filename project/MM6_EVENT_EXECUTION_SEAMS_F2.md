## Complete load is the first execution gate

`scripts/mm6_probe_event_execution_seams.py` joins the existing retained parser, opcode and variable reports to current source hashes. The corpus has 68 EVT files, 14,477 framed records, all 43 active opcode values and 4,285 operands using 127 variable IDs. The current parser has 318 deterministic record rejections across **26 of the 67 listed map EVT files**; `global.evt` is not among them. These 26 files contain 6,964 active records and 1,783 variable operands across 106 distinct IDs. The parser failures are 272 minimum-size rejections, 25 leftover-byte cases, 12 inherited movie-layout cases and nine missing cases; a file can occur in multiple categories.

This is a source-level load barrier, not a claim of a witnessed crash. `EvtProgram::load` in `src/Engine/Evt/EvtProgram.cpp` parses the entire resource and throws on the first bad record. `loadMapEventsAndStrings` in `src/Engine/Engine.cpp` calls it for each map and assigns the result without a title-specific repair. Thus, under the current source, any of those 26 original-equivalent retained event resources prevents construction of that map's complete event program even if the conflicting command would never be reached in play. The other 41 listed map EVT files and `global.evt` pass this **particular** parser-failure screen; that says nothing about correct side effects.

The seven conflicting opcode families remain **12** (MM6 outdoor texture versus inherited movie), **19** (short monster spawn), **20/27/28** (no current parser/executor case), **24** (outdoor facet versus actor flag) and **26** (Question versus inherited input string). The [MMExtension command reference](https://grayface.github.io/mm/ext/ref/) independently identifies MM6 outdoor texture/facet and Question commands, while the pinned [MM6 editor format source](https://github.com/angeld29/mm8leveleditor/blob/bf3b8c4a86100635a5fc6ff53fac6e4e0af5cb53/src/org/gamenet/application/mm8leveleditor/data/mm6/fileFormat/EventFormatMM6.java) is a layout lead with unresolved comments. Neither substitutes for original behavior. The 318 count is *records*, not all map loads or encounters; the 26 count is distinct affected map scripts.

## Executable branch mismatch after parsing

The sole retained opcode-43 `CheckSkill` record has an encoded mastery byte of zero and a required skill level of eight. `EvtInstruction::parse` casts that byte directly to the shared `Mastery` enum, where zero is `MASTERY_NONE`. `EvtInterpreter::executeInstruction` requires both `val.level() >= 8` and exact equality to that mastery. `CombinedSkillValue::isValid` permits `MASTERY_NONE` only at level zero, so the target branch cannot succeed for any valid current skill value. This record is in one of the parser-rejected files, so this is a **second, later** source/data conflict, not a runtime result.

[MMExtension's `evt.CheckSkill` reference](https://grayface.github.io/mm/ext/ref/) says the Novice requirement matches any mastery, which is consistent with a wildcard interpretation for the zero field. That interpretation is a strong lead, not proof of the original MM6 executable's byte mapping or the intended quest branch. F3 must corroborate the field and behavior before F4 locks the rule. The exact event and skill ID stay private.

## Dispatch and persistence chain

After bounded MM6 decoding, the engine still passes opcode 14/16/17/18 variable operands through `EvtInterpreter.cpp` into the inherited `EvtVariables.cpp` vocabulary. The retained variable report places 1,609 operands in MM6-specific ranges where inherited MM7 numeric meanings cannot be trusted. The `Processor.cpp` trigger registry handles timer and map-reload commands separately from ordinary steps, while `EvtProgram::hint` and `canShowTopic` are different read-only paths. Parser success must therefore be followed by **typed MM6 operand validation, correct branch/target selection, state mutation, persistence and visible outcome** for every active opcode and variable family. A clean file or source case does not prove a quest.
