# MM6 house presentation path

Status: F4 display-only MM6 house route, 2026-11-06. The path is compiled and offline-tested; no MM6 process or house screen has been visually observed.

Update, 2026-11-07: **superseded.** The display-only window was replaced by the MM6 house screen in [`MM6House.cpp`](../src/GUI/UI/Houses/MM6House.cpp), which lists services and resident NPC topics. See the [house service gate](MM6_F4_HOUSE_SERVICE_GATE.md). The icon and movie checks below still run before entry. The screen has not been visually observed.

The accepted MM6 room descriptor includes an `npc_picture` field. Referenced descriptors with a nonzero picture ID resolve to an `npc` icon name in the retained MM6 icons directory using the engine's existing minimum-three-digit name convention. An unreferenced descriptor has a candidate icon name absent from the retained index; it is not on a table-backed entry route. The active `SpeakInHouse` ledger includes rooms both with and without proprietor pictures; exact joins remain in ignored private evidence.

`planHouseEntry` carries an optional title-specific proprietor icon name from the MM6 room descriptor. It never substitutes an MM7 room or NPC ID. The MM6 `enterHouse` branch checks icon metadata and movie payload availability before any inherited house state. A missing icon or movie rejects; a zero picture ID has no proprietor icon request. The display-only window now loads and draws the proprietor icon when one exists.

The validated room's `videoName` reaches the existing title-aware movie loader. For MM6, that path resolves an extensionless Smacker entry from exactly one of `Anims1.vid` or `Anims2.vid`; missing or malformed payloads reject before inherited house state. For table-backed entries, `tryOpenHouseMovie` can start the existing house movie loop. If video is disabled or decoding fails, a room with a proprietor icon can still open as a static portrait view; a room with neither display rejects. Blank and terminal plans remain unavailable. The inherited MM7 `pAnimatedRooms` field is not used for the MM6 preview.

The tracked [retained checker](../scripts/mm6_f4_check_house_presentation.py) verifies the private icon index against its frozen media probe hash, the house table against its format-2 probe, and the owner-only room manifest against the house table. It also checks that the staged owner-local `icons.lod` matches the accepted F3 identity report, whose hash is pinned in the F3 gate registry. It prints aggregates only and runs in the one-command offline gate. A private-backed native test checks active entry plans' icon names against the retained index and the with/without-picture classification. A second test reads the staged archive through `LodReader` and decodes all referenced proprietor images. Each image has positive dimensions at most 1024 by 1024, and decoded pixel count agrees with its header. This proves the selected icon payloads can be decoded by the existing engine; it does not place them on screen. The arm64 MM6/OpenEnroth/unit targets built, the focused decode test passed, and the integrated offline and general gates passed without skips. Private test logs retain the exact totals.

The MM6-only `GUIWindow_MM6HousePresentation` draws a staged MM6 panel and exit icon and, when available, the decoded proprietor icon. It installs only an exit button. It does not build inherited shop/guild/transport windows, NPC dialogue buttons, stock, payment or travel actions. The `SCREEN_HOUSE` escape route bypasses inherited dialogue and room sound, preserves the active character, unloads movie playback and closes the window. The entry event also skips inherited house-entry sound for MM6. All other titles retain their prior house path.

The owner-local preflight checks staged MM6 VID archives against accepted F3 identity records before native tests read them. The native room test resolves referenced movies through the same `lookupMovieBlob` path as `MPlayer::LoadMovie`, verifies extensionless Smacker payloads, and rejects missing/duplicate names through the existing lookup contract. This proves media routing and payload presence, not movie frame decoding or rendering.

The arm64 MM6/OpenEnroth/unit targets built with this media preflight. The integrated offline gate passed 185/185 tests from 57 suites without skips (`/tmp/enroth-mm6-f4-house-movie-offline.log`), and the general suite passed 438/438 (`/tmp/enroth-mm6-f4-house-movie-general.log`). No MM6 process or original installation was opened.

The display-only path adds a native activation test across the retained MM6 house table: file-backed rooms create a presentation state, blank or unused rows and terminal handlers reject, and MM7 rejects every MM6 presentation request. A focused exit policy test checks that only the MM6 house screen bypasses legacy dialogue and character advancement. Staged `backevt` and `buttexi1` images decode within their intended screen bounds. The MM6/OpenEnroth/unit targets linked and focused tests passed. Frame visibility and layout still require F5 on-screen inspection; services and save transactions remain gated.

The offline codec probe uses the existing FFmpeg blob I/O and `AVVideoStream` conversion path to decode a first frame without audio or UI. It accepts only Smacker payloads at most 32 MiB, bounds video dimensions to 1024 by 1024, and stops after at most 256 packets. It returns dimensions and decoded buffer size, not image bytes. The staged owner-local VID archives still match accepted F3 identity records. A native test decoded bounded first frames for every referenced room movie, with no failures and no per-movie names in public output. Malformed signatures, invalid headers and a truncated payload still produce no frame. The MM6/OpenEnroth/unit targets built. No private failure report was generated. This does not prove full movie-loop playback, audio, visible rendering, or live game startup. F5 still needs an on-screen check before calling the house route visually verified.
