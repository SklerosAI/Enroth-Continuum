# MM6 first outdoor map preflight — F4

Status: **monitored headless first-world preparation and a bounded outdoor subsystem step pass under scoped test owners; durable new-game save and graphical play remain pending** (2026-11-06).

## Route and checked resources

`Game::loop()` accepts party creation, sets an MM6 pending transition to `oute3.odm`, then calls `saveNewGame()` before `gameLoop()`. That save entry point remains guarded. If it completes later, `gameLoop()` loads portraits and calls `DoPrepareWorld()`. The first map table ID is outdoor under the current dispatch, so the outdoor loader reads its base and `.ddm` delta, then `_461103_load_level_sub()` reaches the still-guarded MM6 chest generator before `onMapLoad()` and the first game frame.

The headless `FirstOutdoorResourcePreflight` reads only private data through the selected engine resources. It checks the table's first outdoor identity, the matching base and delta members, map event/string resources, the minimap image, the loading background, and the base map's sky field and bitmap. It parses the local event program and checks its reload-trigger count, then deserializes the base map into a detached snapshot; it does not call `DoPrepareWorld()`, change live map state, execute event scripts, or write to the installed profile. The lookup identifiers needed by the runtime appear in source and tests; no original bytes or private inventory is tracked.

The MM6 icon archive has one 640×480 loading background. `fullscreenLoadingResources` selects it only for MM6; MM7 still chooses one of its five existing names with the same random draw. MM6 has no corresponding `loadprog` image, so its full-screen loading view draws the background without the inherited progress strip. Progress events still advance internally. The later boxed loading view has an available MM6 background, but no `turnhour` animation in its icon-frame table; it now skips that missing image for MM6 while retaining its numeric progress fill. MM7 loading lookups and draws remain unchanged. This is a presentation gap pending visual acceptance, not a claim that map loading works.

Superseded 2026-11-11: MM6's outdoor loader ignores the sky name in the base map. It shows `sky01` on a first visit, the stored sky on a revisit the same day of the month, and a random `skyNN` from two tables otherwise, all from the 56-byte visit block at the end of the map's delta. `mm6::outdoorSky` in `src/Engine/MM6/MM6OutdoorSky.*` follows that rule for every MM6 outdoor map, and the earlier first-map binding is gone (handoff `agent_comms/handoffs/2026-11-11-claude-mm6-sky.md`).

The first MM6 outdoor map has numeric ID 15, the value named `MAP_SHOALS` in the inherited MM7 enum. The MM7-only Shoals/Lincoln hireling restriction was therefore suppressing the MM6 first-map follower HUD, dialogue, NPC specialty checks and one spell route. All five consumers now pass the selected title to `isHirelingsBlockedOnMap`; MM6 does not inherit those MM7 restrictions, while MM7 retains them exactly. The title-isolation test checks both cases. A separate MM6-specific hireling restriction, if any, would require original rule evidence before implementation.

The first map's reload program contains `SetSprite` actions. MM6 encodes their target as a zero-based map-decoration index; its 28-byte MapSprite record has no MM7 `uCog` field. The inherited MM7 setter searched for `uCog`, which left these MM6 actions ineffective. The event interpreter now uses a bounded index route only for MM6, preserving MM7's cog lookup. A detached test confirms that first-map reload sprite targets fit the decoded decoration array, and a pure test checks visibility, replacement, bounds and title isolation. This follows the [MM6 MapSprite structure and `evt.SetSprite` index calculation in GrayFace MMExtension](https://github.com/GrayFace/MMExtension/blob/9d73c0ff0482bd231ea522f752f4fe9b26640925/Scripts/Structs/01%20common%20structs.lua#L1943-L1981). It still needs live event and visual acceptance.

The reload entry points compare a supported MM6 map byte or quest bit, then branch to a sprite or facet change. The remaining facet branch uses MM6 opcode 12 as an outdoor texture change, not an MM7 movie. The existing MM6 parser and interpreter already decode model/facet operands and route them through a bounded outdoor-face lookup; no semantic change was needed. The detached test checks this branch structure, operand classes, model/facet bounds and bitmap availability. It cannot establish which branch executes on a fresh save or that the replacement renders correctly.

A monitored headless map-load attempt reached `SpawnEncounter` and failed on an MM7-spaced encounter name. MM6's retained map table uses encounter family labels, while its monster text and binary descriptor tables use compact internal variant names; some map labels are display names of a variant rather than internal stems. MM6 spawning now resolves the selected rank through a compact internal-name match, then a unique display-family match, and uses the shared row ID in both MM6 monster tables. It validates the descriptor before allocating an actor and fails closed for missing or ambiguous families. The MM7 name construction and lookup remain intact. A detached headless test checks all three ranks for both first-map encounter families against the loaded MM6 stats and descriptor tables; a pure test covers compact names, display-family fallback, ambiguity, missing names and title isolation. A later retained map uses a family label whose word spacing differs from the display name; the MM6 display comparison now ignores spaces and the detached test checks that one source-backed join. A retained-table sweep still finds five distinct later-map family labels unresolved or ambiguous; this is not complete MM6 encounter coverage.

The five remaining labels have no unique title-table join: two collide across multiple display families and three do not match a compact internal or displayed family. The loader deliberately rejects them if an encounter selects one. A zero-chance map-table cell is not proof that a corresponding scripted or fixed spawn is unreachable. An explicit headless scenario stages default original deltas only in memory, resets the party, initializes the null-renderer loading view and calls `loadAndPrepareODM()` for the first outdoor map. It passes in the linked arm64 GameTest: outdoor level type, map ID, faces and spawnpoints are present. A host monitor observed 135 samples, no focus change and no on-screen process window. The scenario drains nested loading-progress presents with a bounded test-only tick loop; an earlier attempt omitted `DoPrepareWorld`'s AI scratch-array setup, which the fixture now supplies. It does not call the guarded chest generator, run reload events, render a graphical world frame or create a durable save. One nonfatal MM6 voice-index warning remains in the log.

## Live blockers and next acceptance

1. The guarded MM6 `saveNewGame()` must commit a complete `.ec6` transaction and seed `pMapDeltas` before outdoor loading. `OutdoorLocation::Load()` indexes the first `.ddm` in that map; an empty or incomplete delta table would throw before the chest call. This packet does not edit SaveLoad or its transaction.
2. The MM6 chest generator remains guarded in `_461103_load_level_sub()`. A detached resource preflight cannot bypass it or prove the map can finish loading.
3. The scoped `DoPrepareWorld()` scenario now completes first-map preparation and asserts a populated actor collection, but it does not prove exact spawn placement, reload-event effects or a graphical first frame. Five unresolved/ambiguous later-map encounter family labels need source-backed identities before wider map coverage. The existing MM6 UI still has separate minimap-frame, NPC-arrow and other presentation gaps. The boxed loading hour art is omitted safely but still needs a title-specific presentation decision.

The linked headless preflight, outdoor-preparation and scoped full-world scenarios verify resource availability, title isolation, decoded map state and a null-window load. The full-world test checks chest count and actor population, but does not inspect individual reload-event results or a rendered frame. Graphical, audible and save/reload acceptance remain separate.

A separate headless full-world probe uses an explicit first-map pending transition, a ready in-memory CHST owner and `ScopedChestMapLoadOptIn` held only around `DoPrepareWorld()`. It checks the single GUI-window reset precondition, drains at most 256 loading presents and asserts actor/chest/map state after completion. The linked arm64 focused run passed all four world/profession tests; a host monitor recorded 116 samples with no focus change, no on-screen process windows and unchanged frontmost PID. The test asserts outdoor map ID/type, cleared transition, nonempty faces/spawns/actors, 20 chests, one remaining GUI window, null native window and release of the chest opt-in on the loading thread. This does not open the default MM6 chest or save guards. A later combined MM6 suite run exposed lingering process-global state: subsequent save and chest tests failed. The full-world test is therefore disabled by default and must run alone in a fresh GameTest process; no complete world rollback is claimed.

Run that test with `--gtest_also_run_disabled_tests --gtest_filter=MM6Headless.DISABLED_ScopedFirstOutdoorWorld` and the normal MM6 `--game mm6 --headless --data-path ... --rules-path ... --test-path ...` arguments. Do not combine it with other tests in the same process. The regular MM6 suite uses its default filter and omits this test automatically. After the isolation change, the linked arm64 standalone probe passed 1/1; the normal MM6 suite passed 38/38 in a separate process, including the save and chest tests that had failed after shared-state contamination. Host monitors observed respectively 44 and 1,899 samples with no focus change or on-screen process window and unchanged frontmost PID.

## Bounded post-load subsystem step

`MM6Headless.DISABLED_FirstOutdoorSubsystemStep` is a second fresh-process-only test. It enters party creation through the synthetic New Game action, loads portraits as `Game::gameLoop()` normally would, prepares the first outdoor map with in-memory default deltas and scoped chest state, and then exercises a source-selected reload branch. The test chooses an MM6 map-byte comparison whose target is a bounded `SetSprite` instruction, sets that map byte, forces the decoration to the opposite visibility and calls `onMapLoad()` again. The asserted visibility change proves that the selected event ran through the title-specific interpreter. It then advances the null-platform timer, calls `onTimer()` and actor AI, queues a turn and forward action, and calls `UpdateUserInput_and_MapSpecificStuff()`. The party yaw and position change, the action queue drains, and the map transition remains clear.

The linked arm64 test passed 1/1 in a dedicated process. A host monitor observed 123 samples, no focus change, no on-screen process window and unchanged frontmost PID. It is a **subsystem step**, not the first `Game::gameLoop()` frame: the underlying game thread remains in party creation because accepting the party would call guarded MM6 `saveNewGame()`. It also does not call `Engine::DrawGUI()`; that has a separate isolated probe. A nonfatal sound warning appeared for ID 1453 with an empty table name. [AudioPlayer::loadSoundDataSource](../src/Media/Audio/AudioPlayer.cpp) skips loading for an empty name and reports the missing buffer; the upstream call and correct MM6 sound mapping are unresolved. No proprietary audio is included here. Run only with `--gtest_also_run_disabled_tests --gtest_filter=MM6Headless.DISABLED_FirstOutdoorSubsystemStep` and the normal private MM6 headless arguments, with no other tests in the same process.

The first full-world attempt exposed a real menu-window ownership precondition. The persistent main-menu state owns one window separately from `pGUIWindow_CurrentMenu`, so the probe now sends the synthetic New Game action and waits for party creation to own the only extra window before `DoPrepareWorld` resets it. This transition creates the default party but stops before the normal guarded new-game save. A subsequent monitored run passed that precondition and reached additional peasant NPC generation, then aborted on `random(0)`: MM6 initialization had never filled `pProfessionChance`. The retained MM6 archive has no `npcdist.txt`; its `npcprof.txt` has a Chance column documented by [MMExtension's MM6 NPC profession structure](https://grayface.github.io/mm/ext/ref/). The MM6 loader now checks those numeric weights, excludes the nonnumeric terminal profession, rejects invalid or empty distributions and uses the resulting range for wandering peasant selection. The MM7 per-map `npcdist.txt` path and profession range remain separate. Applying the MM6 table's global weights to every map is an inference from this table shape, not yet a claim about the original executable's map-specific generation behavior. The linked rerun passed. A nonfatal party-creation `aframe1` resource warning remains; the separate MM6 presentation route needs visual acceptance.
